# Agent report — Product Auditor

**What I inspected:** 8 domain groups of the frontend (shell/routing/auth, design tokens + shadcn kit, dashboard, events, registrations, form builder, payments, settings/admin).

**What I changed:** Nothing (read-only).

**Key outputs:** `docs/product-audit.md` (route/component/workflow/API/risk inventory).

**Highest redesign risks flagged:
- (high) [App Shell, Routing & Auth] Theming (next-themes not wired): next-themes is installed and darkMode:'class' is set with a full .dark CSS-var block, but NO ThemeProvider is mounted anywhere and nothing toggles the .dark class. Only ui/sonner.jsx imports useTheme (defaults to 'system'). Dark mode is effectively dead code today. Any redesign that turns on theming must add a ThemeProvider at the App root and a toggle, and reconcile the fact that Tailwind's primary/secondary/accent are HARDCODED HEX (not hsl(var(--x))), so they will NOT respond to the .dark variables — the brand navy would stay fixed while shadcn neutrals flip. This is a real inconsistency to resolve before enabling dark mode.
- (high) [App Shell, Routing & Auth] Auth: ProtectedRoute has no role/campaign enforcement: ProtectedRoute only checks that a user exists. Role gating (super_admin-only pages like /users, /control-panel, /fund-transfers, /approvals) and campaign-access checks are NOT enforced at the router — they depend on each page calling isSuperAdmin/canWrite/canAccessCampaign, or on the backend rejecting. AppLayout merely hides nav links for non-super-admins, but the routes remain directly reachable by URL. A redesign should not assume the router protects these; introducing a role-aware guard is a security improvement but must replicate the existing page-level checks exactly to avoid regressions.
- (high) [Design Tokens & shadcn UI Kit] tailwind.config.js color object vs index.css CSS vars: The whole design system has two sources of truth that disagree. Changing brand colors in only one place produces no effect or half-applied effects (e.g. editing --primary in index.css does nothing because bg-primary reads the hex). A redesign must unify these — ideally drive tailwind colors from the CSS vars — but doing so will shift every color that currently relies on the config hex.
- (high) [Design Tokens & shadcn UI Kit] Extended token names baked into hundreds of call sites: primary-hover/primary-subtle/primary-active/secondary-subtle/accent-subtle and the brand.* + slate ramp are referenced directly across pages and FormBuilder. Renaming or removing any token silently drops styles (Tailwind emits nothing for an unknown class). Grep-verified usage in CampaignModals, ErrorBoundary, FieldEditor, FieldRules, FormPreview, FormulaBuilder.
- (high) [Dashboard & Analytics] src/utils/dashboardStats.js (all compute* fns) + Dashboard useMemo: ALL analytics business logic lives in the frontend, not the backend AnalyticsController. Redesign must preserve exact semantics: NET_FEE_RATE=0.0295 net-revenue math, conversion=paid/total, avgValue, local-midnight daily bucketing (400-bucket cap), gateway/collection/event-status attribution via campaign metadata. This is not just UI — it is the product's numbers.
- (high) [Dashboard & Analytics] Data model coupling: campaign_id->campaignId rename + name stitching: Dashboard depends on GET /dashboard/registrations-summary returning specific fields (id, campaign_id, payment_status, total_amount, created_at, name) and manually joins campaign name/gateway/collection-method/status from GET /campaigns. Splits and top-events break silently if campaign metadata fields (payment_gateway, payment_collection_method, status, slug) change.
- (high) [Dashboard & Analytics] Excel export pipeline (Dashboard.js ~lines 94-255): ~160 lines of dense business logic embedded directly in the page component: N+N sequential-ish fetches per campaign, per-campaign form-field label/type/option resolution, rich_text/name/object/choice flattening. Fragile, hard to test, and easy to break in a redesign; should be extracted to a service/hook before any UI rewrite.
- (high) [Events / Campaigns] CampaignDetail.js size/coupling: ~1774-line file mixing presentation, data fetching, 3 modals, analytics charts, and 3 inline sub-components (RegistrationWindowEditor/FormTypeEditor/RegistrationStatusToggle). Any redesign must decompose carefully; high regression surface.
- (high) [Events / Campaigns] Revenue fee math embedded in UI: Net revenue computed in-component: Campaigns.js calculateNetRevenue (total*0.0295 fee) and CampaignDetail multiplies total_revenue*0.9705 and avg*0.9705. Hardcoded 2.95% gateway fee in the view; must be preserved exactly and ideally moved server-side.
- (high) [Events / Campaigns] Registration window timezone logic: RegistrationWindowEditor does bespoke UTC<->local wall-clock conversion (parseServerDate/toISOString) with guards against single-date clearing and open>=close. Subtle; easy to break during redesign and would silently shift stored times.
- (high) [Events / Campaigns] Custom ID counter rewind guard: EditCampaign only sends registration_next_number/invoice_next_number when changed from loaded value; sending unchanged value rewinds live counters causing duplicate IDs. Business-critical invariant baked into submit handler.
- (high) [Events / Campaigns] Free-vs-paid payload normalization: Create/Edit null out fund_collection_mode, payment_account_id, payment_purpose, and force payment_collection_method='online' when free; comments note backend also treats empty string as CLEAR vs null as no-change. Fragile field-semantics contract that must be preserved.
- (high) [Events / Campaigns] Role gating scattered inline: isSuperAdmin() and user.role checks are sprinkled through JSX producing two divergent detail layouts (super_admin vs org_admin) and redirects in Create/Edit/Settings. Easy to leak privileged controls if refactored blindly.
- (high) [Registrations, Members & Kiosk] KioskMode.js pricing (calculateTotal, safeCustomAmount): Business-critical price math embedded directly in the UI component — sums base_price + option price_modifiers + custom_amount and must mirror the public form and server exactly. A comment even notes a past clamping bug. Any redesign that refactors this loses parity risk.
- (high) [Registrations, Members & Kiosk] CampaignRegistrations edit flow (handleSaveEdit): Refund/additional-payment side effects are driven off response fields (refund_required, refund_amount, payment_link) with money-facing toasts and auto clipboard copy. Financial workflow logic is entangled in the modal; must be preserved bit-for-bit.
- (high) [Registrations, Members & Kiosk] KioskMode OTP verification (verifyOtp): Security-sensitive: does a client-side plaintext OTP comparison (selectedResult.otp) BEFORE/alongside backend /verify-otp, meaning the OTP is shipped to the client and can be bypassed if the object is inspected. Redesign should not entrench this; flag for security review.
- (high) [Registrations, Members & Kiosk] CampaignMembers.js undefined Clock import: Line ~599 renders <Clock className=...> in the Last Reminder cell but Clock is NOT imported in the lucide-react import block — this is a latent ReferenceError/crash when a member has last_reminder_at set. Redesign must add the import or it stays broken.
- (high) [Form Builder, Landing Page Builder & Email Templates] usePublicForm.calculateTotal (hooks/usePublicForm.js:279): Client-side pricing uses raw eval() on a formula string; business-critical pricing/coupon logic is embedded in a shared hook that must stay byte-for-byte in sync with the server formula engine and couponPricing.js. Any redesign that touches this hook risks price/amount-mismatch failures at the payment gateway.
- (high) [Form Builder, Landing Page Builder & Email Templates] LandingPageBuilder.js (1953 lines, single file): SectionPreview is a ~950-line if/else render function with 30+ hardcoded per-template layout branches and heavy inline styling. Sample data, template-style detection (layoutMappings), and all rendering live in one monolith — very hard to restyle without regressions; no component decomposition.
- (high) [Form Builder, Landing Page Builder & Email Templates] FieldEditor.js (1231 lines) + createDefaultField: Enormous per-field settings component with deeply type-specific branches (name_config, phone country lists, custom_amount gateway clamping on blur, validation-message keys). Business rules (gateway min/max, 5MB/25MB file caps, mask/case transforms) are embedded in the UI, not a schema. Restyling must preserve all conditional blocks exactly.

**Next agent (Design System) requirements:** unify the token layer (index.css CSS vars vs tailwind.config.js hex conflict); brand secondary/accent/muted (currently grey); make dark theme navy; brand chart vars; remove purple leftovers.
