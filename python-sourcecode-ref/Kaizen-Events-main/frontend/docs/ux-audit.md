# Kaizen Events — UX Heuristic Audit (Frontend)

> Phase 1 UX evaluation against Nielsen's 10 heuristics + UX laws (Fitts, Hick, Gestalt, cognitive load, progressive disclosure). Findings are recommendations only — nothing was implemented.

**Total findings:** 123 — CRITICAL 6 · HIGH 40 · MEDIUM 59 · LOW 18

## Top priority findings (CRITICAL + HIGH, all groups)

### 1. [CRITICAL] A failed initial load fires a single sonner toast ('Failed to load dashboard data') and then renders the full dashboard with every KPI at 0, an empty donut ring, and empty tables. There is no page-level error state and no retry affordance. A zeroed dashboard from a network/auth failure is visually identical to a legitimately empty account.
- **Group / page:** Dashboard & Analytics — /dashboard (src/pages/Dashboard.js, fetchDashboardData catch block ~L80-84)
- **Principle:** Nielsen #1 Visibility of system status; #9 Help users recognize, diagnose and recover from errors
- **Why it matters:** This is the admin's primary daily overview and the numbers drive real decisions (revenue, pending payouts, conversion). If the toast is missed or auto-dismisses, the admin will read ₹0 revenue and 0 registrations as fact and either panic or make a wrong call. Silent, indistinguishable failure destroys trust in every number on the screen.
- **Recommendation:** Add an explicit page-level error state: on catch, set an error flag and render a distinct panel ('Couldn't load dashboard data') with a Retry button that re-runs fetchDashboardData, instead of falling through to the zeroed view-model. Distinguish 'load failed' from 'no data yet' visually.

### 2. [CRITICAL] Export to Excel only applies the Event (campaign) filter — it ignores the active date-range and payment-status filters. The dashboard shows filtered numbers (e.g. 7D + Paid), but clicking Export downloads every registration for the selected campaign(s) across all time and all statuses. The Export button sits directly beside the filters, implying it exports the current view.
- **Group / page:** Dashboard & Analytics — /dashboard (src/pages/Dashboard.js handleExportExcel ~L100-102; only filters by selectedCampaign)
- **Principle:** Nielsen #2 Match between system and the real world; #4 Consistency and standards (WYSIWYG expectation)
- **Why it matters:** Admins routinely filter to a period/status and export what they see for reporting or reconciliation. Getting a silently wider dataset than the on-screen view produces wrong reports and undermines confidence in both the dashboard and the export. The mismatch is invisible until someone cross-checks totals.
- **Recommendation:** Either apply dateRange and statusFilter to the export set so it matches the visible view, or make the scope explicit on the button/label (e.g. 'Export all records for this event') and confirm the intended scope before download. Preferred: honor all three active filters.

### 3. [CRITICAL] The 'Last Reminder' cell renders <Clock .../> but Clock is never imported in CampaignMembers.js (import block at lines 8-13 omits it). The moment any member row has a last_reminder_at value, React throws a ReferenceError and the entire Members table unmounts to a blank/crash screen.
- **Group / page:** Registrations, Members & Kiosk — CampaignMembers.js (Member Management, /campaigns/:campaignId/members)
- **Principle:** Nielsen #5 Error Prevention / #9 Help users recognize & recover from errors (latent runtime crash)
- **Why it matters:** Sending reminders is the core daily job of this page. As soon as an admin sends the first reminder, that member gets last_reminder_at set, so the very next render of the table crashes. The feature breaks precisely when it starts being used, and the admin sees a white screen with no recovery path.
- **Recommendation:** Add Clock to the lucide-react import. Then wrap page-level rendering in an error boundary so a single bad cell degrades gracefully instead of blanking the whole management screen. Add a smoke test that renders a member with last_reminder_at set.

### 4. [CRITICAL] The Form Builder uses two contradictory persistence models on one screen. Editing a field in the right panel calls updateField() which silently persists the ENTIRE form to the server immediately (persistForm), while reordering (handleDragEnd just setFields), duplicating, deleting, changing Base Price, banner/header/logo images, theme colors, and section title only mutate local React state and persist when the admin scrolls down and clicks 'Save Form'. There is no visual distinction between the auto-saved and the not-yet-saved changes.
- **Group / page:** Form Builder, Landing Page Builder & Email Templates — FormBuilder (/campaigns/:campaignId/form-builder)
- **Principle:** Nielsen: Visibility of system status; Consistency & standards; Error prevention; User control and freedom
- **Why it matters:** An admin who drags fields into a new order, deletes a field, or sets the base price and then navigates away (or the session 401-redirects to /login via the axios interceptor) loses that work with zero warning — but a label edit they made moments earlier is already saved. This split model is invisible and produces silent, hard-to-diagnose data loss on the single most-used builder screen. The audit itself flags this as a high-severity rewrite risk; as UX it is a daily correctness hazard.
- **Recommendation:** Adopt one model. Either make every mutation dirty-flag local state and save only on explicit Save (preferred for a builder), or auto-save everything. Track a single isDirty flag, show an 'Unsaved changes' indicator on the Save button, and add a route-leave/beforeunload guard. Do not silently persist the whole form on a per-field save while leaving reorders volatile.

### 5. [CRITICAL] There is no unsaved-changes protection anywhere in the builders. FormBuilder and LandingPageBuilder hold ~20 useState slices with no isDirty tracking, no beforeunload handler, and no React Router navigation block. The only save affordance is a non-sticky button at the very bottom of the scrolling canvas.
- **Group / page:** Form Builder, Landing Page Builder & Email Templates — FormBuilder; LandingPageBuilder (/campaigns/:campaignId/landing-page)
- **Principle:** Nielsen: Error prevention; Visibility of system status
- **Why it matters:** Building a form or landing page is long, high-effort work. A misclick on 'Back to Event', a browser back gesture, a token-expiry redirect, or a tab close discards everything not yet saved. Because save is inconsistent (previous finding), admins cannot even reason about what is safe to lose.
- **Recommendation:** Add a dirty-state tracker and a confirm-on-leave guard (beforeunload + Router blocker). Surface a persistent 'You have unsaved changes' state on the Save button and disable it when clean.

### 6. [CRITICAL] In UserManagement, the Edit action is available on every row including the signed-in admin's own super_admin/Director row. A Super Admin can open their own record, switch Role from 'Super Admin' to 'Org Admin' (or clear their own campaign access), hit Save, and instantly strip their own privileges with no warning and no confirmation. There is no 'this is you' guard and no re-fetch of self.
- **Group / page:** Settings, Admin, Integrations & Auth pages — UserManagement.js (openEditModal / handleSubmit)
- **Principle:** Nielsen #5 Error Prevention (and #3 User Control & Freedom - no undo for a destructive self-action)
- **Why it matters:** This is an irreversible self-lockout in a daily-use tool: the moment the update returns, the client-side gates (isSuperAdmin, can_approve_transfers) fail and the admin loses access to UserManagement itself, so they cannot undo it. In a small admin team this can lock the whole organisation out of user administration and require a DB-level fix.
- **Recommendation:** Detect editing self (compare listUser.id to useAuth().user.id) and either disable the Role select + Director checkbox for your own row, or require an explicit typed confirmation ('You are about to remove your own admin access'). Never allow self-demotion silently; keep the current 'Delete hidden for super_admin/Director' logic consistent by also protecting self-edit.

### 7. [HIGH] The global nav (AppLayout top bar) exposes only Dashboard, Events, and — for super_admin — Fund Transfers and Control Panel, yet the app has ~60 authenticated routes (registrations, members, campaign settings, email templates, offline payments, payment accounts, users, approvals, activity logs, integrations, DKIM, kiosk volunteers, etc.). Every one of these is reachable only by in-page links or by typing a URL. There is no global map of the product.
- **Group / page:** App Shell, Routing & Auth — AppLayout.js (top nav) — affects all authed routes
- **Principle:** Nielsen: Recognition rather than recall; Visibility of system status; plus Hick's Law (no structured menu to choose from) and task-efficiency
- **Why it matters:** Admins do their daily work in the deep routes, not on the two links that are surfaced. Forcing them to remember which page links to which, and to click through intermediate screens to reach a common destination, adds navigation cost to every task and makes large parts of the app effectively undiscoverable. New admins cannot form a mental model of what the system can do.
- **Recommendation:** Introduce a persistent, grouped primary navigation (a left sidebar on desktop reusing the existing mobile drawer markup) with sections such as Overview, Campaigns, Finance (Payment Accounts, Fund Transfers, Offline Payments, Instamojo), People (Users, Members, Kiosk Volunteers), and Control Panel. Drive it from a single data-driven nav config so desktop and drawer stay in sync, and gate items by role there instead of only in the top bar.

### 8. [HIGH] Once an admin is inside a campaign (/campaigns/:id, /registrations, /members, /settings, /form-builder, /landing-page, /email-templates/:trigger, /offline-payments) there is no campaign-scoped subnavigation and no persistent indication of which campaign they are working in. Each is a flat top-level route with only the thin global top bar.
- **Group / page:** App Shell, Routing & Auth — All /campaigns/:campaignId/* routes
- **Principle:** Nielsen: Visibility of system status; Recognition rather than recall; Gestalt (common region / grouping)
- **Why it matters:** Campaign work is the core daily loop, and admins routinely juggle several campaigns. With no campaign name shown and no tabs to move between a campaign's registrations, members, settings and templates, users must back out to the campaign list and re-enter, and they risk editing the wrong campaign's settings because nothing confirms context.
- **Recommendation:** Add a campaign layout route (React Router v7 nested layout with <Outlet>) that renders a header showing the current campaign name/status plus a horizontal sub-nav (Details, Registrations, Members, Form, Landing Page, Email Templates, Settings, Offline Payments). This keeps context visible and makes intra-campaign navigation one click.

### 9. [HIGH] When any API call returns 401 (e.g. the 30-minute access token expires mid-task), the axios response interceptor silently clears localStorage and does window.location.href='/login' with no toast, no explanation, and no return-path. The same hard redirect happens for the general case with zero user-facing message.
- **Group / page:** App Shell, Routing & Auth — services/api.js (401 interceptor) — affects every authed page
- **Principle:** Nielsen: Help users recognize, diagnose, and recover from errors; Visibility of system status; Error prevention
- **Why it matters:** An admin filling a long form or reviewing registrations is dumped to the login screen with no reason given and any unsaved work lost. Because there is no refresh-token rotation on the client, this will happen predictably every 30 minutes of a working session. Users experience it as the app 'randomly logging me out' and cannot tell it apart from a real error.
- **Recommendation:** On 401, show a toast ('Your session expired — please sign in again') before redirecting, and preserve the attempted location as a ?next= param so the user returns to where they were after re-login. Longer term, add silent token refresh so routine expiry never surfaces as a logout.

### 10. [HIGH] Role-restricted pages (/users, /control-panel, /fund-transfers, /approvals) are hidden from the nav for non-super-admins, but ProtectedRoute enforces only presence of a user — the routes remain directly reachable by URL and rely on each page or the backend to reject.
- **Group / page:** App Shell, Routing & Auth — ProtectedRoute.js + role-gated routes (/users, /control-panel, /fund-transfers, /approvals)
- **Principle:** Nielsen: Consistency and standards; Error prevention; Help users recognize/recover from errors
- **Why it matters:** Hiding the link while leaving the route open creates an inconsistent, confusing experience: a bookmarked or shared URL, or a stale link, drops an org_admin onto a page that may render partially, error obscurely, or show an empty shell before the backend refuses. The user gets no clean 'you don't have access' state. It is both a UX inconsistency and a latent authorization gap.
- **Recommendation:** Add a role-aware guard (wrapping or extending ProtectedRoute) that replicates the existing isSuperAdmin/canWrite/canAccessCampaign checks and renders a clear 403 page for unauthorized users, instead of relying solely on nav-hiding plus backend rejection. Keep server-side checks as the real authority.

### 11. [HIGH] The shadcn `accent` token, which every primitive uses for hover and selected states, has been overridden in tailwind.config.js from a subtle neutral to a fully saturated gold (#CC9E4A). Because `bg-accent`/`hover:bg-accent` drive dropdown-menu item hover, select-option hover, ghost- and outline-button hover, dialog/sheet close-button hover, and command/list highlighting, routine pointer interactions across the admin now flash loud gold blocks. In stock shadcn these surfaces are a quiet grey.
- **Group / page:** Design Tokens & shadcn UI Kit — Global - every shadcn menu, select, dropdown, ghost/outline button and dialog across the admin (dashboard, registrations table, form builder)
- **Principle:** Nielsen #4 Consistency & standards; #8 Aesthetic & minimalist design; visual hierarchy / signal-to-noise; cognitive load
- **Why it matters:** An admin scanning a payments table, opening a status dropdown, or moving through a form-builder toolbar sees saturated gold bars appear on every hover. Gold is the brand's rarest accent, so using it as the default hover fill destroys visual hierarchy: the eye is pulled to whatever the cursor grazes rather than to real state or primary actions. High-frequency, low-importance interactions become the loudest thing on screen, increasing visual noise and cognitive load during repetitive daily work (reconciling registrations, editing fields).
- **Recommendation:** Restore `accent` to a subtle neutral (map `bg-accent` to the grey `--accent`/`--muted` HSL var as shadcn intends) and reserve the gold #CC9E4A for a dedicated brand token (e.g. `bg-gold`/`bg-brand-gold`) used deliberately for emphasis, not for default hover. Keep `accent-foreground` paired accordingly so hover text contrast stays correct.

### 12. [HIGH] The `secondary` token is overridden to deep crimson red (#9E0E18), so every `variant="secondary"` button and `secondary` badge renders bright red - while the truly destructive `destructive` token is also red (hsl(0 84% 60%)). Non-dangerous secondary actions and the delete/destructive action are now both red and easily confused.
- **Group / page:** Design Tokens & shadcn UI Kit — Global - all secondary buttons and secondary badges; destructive actions on registrations, campaign members, payments
- **Principle:** Nielsen #2 Match between system and real world (colour semantics); #5 Error prevention; affordance
- **Why it matters:** Red is a near-universal danger/stop signal. When ordinary secondary buttons (cancel, alternate submit, filter toggles) and status badges appear in crimson, admins get false danger cues and hesitate, and - more seriously - genuine destructive buttons (delete registration, remove member, void payment) no longer stand out as the one red thing. This erodes error prevention on exactly the irreversible actions where distinctiveness matters most.
- **Recommendation:** Do not use a saturated danger-red as the generic `secondary` surface. Either give `secondary` a neutral/tinted treatment and expose crimson as an explicit brand token, or make destructive visually unambiguous (distinct hue/weight, icon, or confirm affordance) so it is never mistaken for a benign secondary button. Audit call sites so no delete control renders in the same red as a routine secondary button.

### 13. [HIGH] The dashboard payment-status donut (StatusDonut.js) encodes Paid as green (#16a34a) and Failed as red (#dc2626) and distinguishes slices by colour alone, with no tooltip on the pie. The two most decision-critical statuses are a red/green pair - indistinguishable to red-green colour-blind users (~8% of men) within the ring itself.
- **Group / page:** Design Tokens & shadcn UI Kit — Dashboard (StatusDonut on the analytics/overview page)
- **Principle:** Accessibility (WCAG 1.4.1 Use of Colour, colour-blind safety); Nielsen #2 Match real world; don't rely on colour alone
- **Why it matters:** Payment reconciliation is a core daily admin task. A colour-blind admin cannot tell the paid slice from the failed slice by looking at the donut, and with no hover tooltip they cannot inspect a slice to disambiguate. The legend does pair colour swatches with text labels (a partial mitigation), but the swatches share the same red/green problem, so the at-a-glance donut - the whole point of the chart - fails for those users.
- **Recommendation:** Add a Recharts <Tooltip> to the donut so any slice can be inspected, and differentiate statuses by more than hue - e.g. add value/percentage labels, pattern fills, or a colour-blind-safe palette (avoid the red/green pair for the primary paid-vs-failed distinction). Drive these from a shared, documented status palette rather than inline hex.

### 14. [HIGH] handleRefresh always shows the success toast 'Dashboard refreshed' after awaiting fetchDashboardData, even when that fetch failed. Because fetchDashboardData swallows its own error and shows 'Failed to load dashboard data', a failed refresh produces two contradictory toasts back to back.
- **Group / page:** Dashboard & Analytics — /dashboard (src/pages/Dashboard.js handleRefresh ~L87-92 vs fetchDashboardData catch ~L80)
- **Principle:** Nielsen #1 Visibility of system status; feedback accuracy
- **Why it matters:** Contradictory feedback ('failed' + 'refreshed') on the core refresh action leaves the admin unsure whether the data on screen is current or stale. On a page whose entire value is trustworthy live numbers, ambiguous success signalling is actively misleading during the daily check.
- **Recommendation:** Have fetchDashboardData return/throw a success signal and only toast 'Dashboard refreshed' when it actually succeeded; on failure show the error toast alone. Consider replacing the toast with an inline 'Updated HH:MM' stamp.

### 15. [HIGH] When a filter combination yields no rows (e.g. Status=Failed + 7D on a healthy account), the whole dashboard collapses to zeros/empties with no unified message and no way to clear filters. Empty handling is scattered and inconsistent across widgets: TopEventsTable says 'No events yet', RecentRegistrations says 'No registrations yet', StatusDonut shows an unlabeled grey ring, KPIs show 0. There is no 'Clear filters' / reset control anywhere.
- **Group / page:** Dashboard & Analytics — /dashboard (src/pages/Dashboard.js filter bar + vm; widgets TopEventsTable.js, RecentRegistrations.js, StatusDonut.js)
- **Principle:** Nielsen #9 Error recovery; #3 User control and freedom; error prevention
- **Why it matters:** A filtered-to-empty state reads as 'the app is broken' or 'we have no data', not 'your filter excluded everything'. With three independent filters and no reset, an admin can strand themselves in an empty view and not realize a stale filter is the cause. This is a frequent daily friction point.
- **Recommendation:** Add a unified empty state distinct from the error state ('No registrations match these filters') shown when filters exclude all rows, plus a single 'Clear filters' button (and/or per-filter active chips) to reset date/event/status in one click.

### 16. [HIGH] The dashboard is saturated with 10-11px sub-labels and captions rendered in text-slate-400 (#94a3b8) on white — KPI labels/sub-lines, chart captions, donut 'total', Top Events sub-stats, Recent Registrations event/time lines. #94a3b8 on #ffffff is roughly a 2.8:1 contrast ratio, below the WCAG AA 4.5:1 minimum for normal text (and these are also very small).
- **Group / page:** Dashboard & Analytics — /dashboard and all widgets (KpiTile.js L9/L18, TrendChart axes, StatusDonut L27, TopEventsTable L43, RecentRegistrations L27)
- **Principle:** Accessibility / WCAG 2.1 AA contrast (1.4.3); legibility, visual hierarchy
- **Why it matters:** The metadata that tells the admin what each number means (labels, time, 'paid / regs') is the least legible content on the page. Low-contrast micro-type is hard to read for anyone under glare or over 40, and formally fails accessibility. On a data-dense operational screen, unreadable labels turn numbers into guesswork.
- **Recommendation:** Darken secondary text to at least slate-500/600 (≥4.5:1) and raise the smallest sizes from 10-11px toward 12px. Define these as theme text tokens rather than ad-hoc text-[10px]/slate-400 so the ratio is enforced consistently.

### 17. [HIGH] The "Revenue" stat silently subtracts a hardcoded 2.95% gateway fee (Campaigns.js calculateNetRevenue, and CampaignDetail total_revenue*0.9705 / average*0.9705) but is labeled only "Revenue" with no indication the figure is net-of-fee.
- **Group / page:** Events / Campaigns — Campaigns.js (list cards), CampaignDetail.js (Revenue stat card)
- **Principle:** Nielsen: Match between system and real world + Visibility of system status; financial-data honesty/error prevention
- **Why it matters:** Admins reconcile these numbers against gateway payouts and their own bookkeeping daily. A number that is 2.95% lower than gross with no label reads as a bug or erodes trust in the whole dashboard, and the fee is invisible so no one can tell whether it applies to free/organizer-direct events too (where a platform fee may not apply at all).
- **Recommendation:** Label the figure "Net Revenue (after 2.95% platform fee)" or show gross with the fee as a sub-line, and add a tooltip. Only apply the discount where a platform fee actually applies (kaizen_managed), not to every campaign uniformly. Ideally source the net figure from the backend rather than recomputing 0.9705 in the view.

### 18. [HIGH] The activation requirement (all 4 email templates must be filled before an event can go active) is only discoverable by attempting to activate and receiving a 400, surfaced as an error toast with a jump link. Nothing on the detail or edit page signals beforehand that the event is not ready to go live.
- **Group / page:** Events / Campaigns — EditCampaign.js (submit catch), CampaignDetail.js (Activate Event quick action)
- **Principle:** Nielsen: Error prevention + Visibility of system status + Help users recognize/recover
- **Why it matters:** Going live is the single most important campaign task. Making admins fail first to learn the prerequisite adds a frustrating trial-and-error loop, and the requirement is completely invisible until the failure fires. On the detail page the Activate button gives no hint it will be rejected.
- **Recommendation:** Show a persistent readiness checklist on the detail page ("Before activating: 4/4 email templates, payment account, form configured") with direct links, and disable/annotate the Activate button when prerequisites are unmet rather than letting the click fail.

### 19. [HIGH] Create and Edit are single, very long scrolling forms whose sections appear and disappear based on payment_enabled, payment_collection_method, fund_collection_mode and payment_account_id. There is no step wizard, no section navigation, no progress indicator, and no on-screen summary of what has been configured.
- **Group / page:** Events / Campaigns — CreateCampaign.js, EditCampaign.js
- **Principle:** Progressive disclosure, Hick's Law, cognitive load, Gestalt (grouping)
- **Why it matters:** Setting up an event is a high-stakes, multi-decision task. Conditional sections that pop in/out mid-scroll cause the page to jump and make it hard to know what is left to fill or why a field vanished. Admins lose their place and cannot see the whole configuration at a glance.
- **Recommendation:** Break the flow into a lightweight stepper or anchored section nav (Basics / Pricing & Payment / Registration / Advanced IDs) with a persistent progress/summary rail, keeping conditional reveals within their step so the layout stops jumping.

### 20. [HIGH] Required-field validation on Create/Edit only fires on submit as a single sonner toast (e.g. "Please select a fund collection mode"); there are no inline field-level errors and no auto-scroll to the offending field. The only always-visible cue is a small red line under fund mode.
- **Group / page:** Events / Campaigns — CreateCampaign.js, EditCampaign.js
- **Principle:** Nielsen: Error prevention + Help users recognize and recover from errors
- **Why it matters:** On a form this long, a toast that names one problem forces the admin to hunt up and down the page for the field, and other missing fields are only revealed one at a time. This is slow and error-prone for the most repeated create/edit workflow.
- **Recommendation:** Add inline validation messages anchored to each field, mark all invalid fields at once on submit, and scroll to / focus the first invalid field.

### 21. [HIGH] The detail console is one ~1774-line page that stacks stats, two charts, registration + kiosk URL blocks with QR, the registration-window editor, a four-section Quick Actions grid, fund management, event history, and three modals on a single scroll with no tabs or collapsing.
- **Group / page:** Events / Campaigns — CampaignDetail.js
- **Principle:** Cognitive load, progressive disclosure, Nielsen: Recognition rather than recall, Aesthetic and minimalist design
- **Why it matters:** Daily management tasks (open kiosk, toggle registration, export, change payment account) are buried at different scroll depths, and every visit forces the admin to re-scan a dense wall to find one control. Frequent tasks have no shortcut and low findability.
- **Recommendation:** Introduce tabs or collapsible sections (Overview / Links & QR / Registration / Payments & Kiosk / Team / History) and hoist the 3-4 most-used actions into a compact always-visible action bar in the header.

### 22. [HIGH] The Next Registration Number / Next Invoice Number inputs let a super admin type any value, and the helper text only says "Changing this only affects future registrations." The invariant that lowering the counter rewinds live IDs and produces duplicate registration/invoice numbers is enforced only by invisible submit-handler logic, never surfaced to the user.
- **Group / page:** Events / Campaigns — EditCampaign.js (Custom IDs section)
- **Principle:** Nielsen: Error prevention + Help/documentation
- **Why it matters:** Duplicate invoice/registration IDs are a serious, hard-to-undo data-integrity and compliance problem. The current helper text actively understates the risk, so an admin correcting a typo could set the counter backwards with no warning.
- **Recommendation:** Show the current live counter as read-only context, warn inline when the entered value is <= the loaded value ("This is below the current counter and will cause duplicate IDs"), and require an explicit confirm before decreasing.

### 23. [HIGH] The two export buttons silently produce different data sets. 'CSV' calls the backend endpoint /export/csv with no filter parameters (exports ALL registrations), while 'Export Excel' is built client-side from filteredRegistrations (exports only the currently filtered/searched rows). Same toolbar, same mental model ('export what I'm looking at'), two different results.
- **Group / page:** Registrations, Members & Kiosk — CampaignRegistrations.js (handleExportCSV vs handleExportExcel)
- **Principle:** Nielsen #4 Consistency & Standards / #1 Visibility of System Status
- **Why it matters:** An admin who filters to 'Failed / Last 7 days' and clicks CSV gets the entire campaign; the same click on Excel gets the 12 filtered rows. Neither button tells you its scope, so reconciliations, refund lists, and finance handoffs can be built on the wrong population without anyone noticing.
- **Recommendation:** Make both exports honor the active filters (pass status/date/search to the CSV endpoint, or filter client-side identically). Label each button with its scope, e.g. 'Export filtered (12)' vs 'Export all (840)', so the row count is visible before the click.

### 24. [HIGH] The Revenue analytics card multiplies total_revenue by a hardcoded 0.9705 (line 543), but the Excel 'Summary' sheet exports the raw, unmultiplied total_revenue (line 328). The number an admin reads on screen and the number in the exported report for the same metric disagree by ~3%.
- **Group / page:** Registrations, Members & Kiosk — CampaignRegistrations.js (Revenue card & Excel Summary sheet)
- **Principle:** Nielsen #4 Consistency & Standards / #2 Match between system and real world
- **Why it matters:** Revenue is the number people screenshot, forward, and reconcile. When the dashboard says one figure and the export says another with no explanation of the magic multiplier, admins lose trust in the whole analytics panel and can't tell which figure is authoritative for finance.
- **Recommendation:** Compute the displayed revenue once (server-side, named e.g. net_revenue) and use that single value in both the card and the export. If the 0.9705 is a gateway-fee net, label the card 'Net Revenue (after fees)' and show gross alongside so the number is legible rather than mysterious.

### 25. [HIGH] When an edit increases the amount, the generated additional-payment link is never shown in the UI. handleSaveEdit silently does navigator.clipboard.writeText(result.payment_link) and fires a toast; the modal then closes. There is no field displaying the link and no way to retrieve it again.
- **Group / page:** Registrations, Members & Kiosk — CampaignRegistrations.js (handleSaveEdit, line ~398-404)
- **Principle:** Nielsen #1 Visibility of System Status / Feedback
- **Why it matters:** The link is the entire point of the action, yet it exists only on the clipboard for a few seconds. If the clipboard write is blocked (non-secure context / permissions), the toast still says success and the link is lost forever. The admin must redo the edit or contact support to recover a payment URL they were told was 'generated'.
- **Recommendation:** Show the payment link in a persistent panel (or a follow-up dialog) with a visible URL, an explicit Copy button that confirms success, and secondary actions (email/WhatsApp to registrant). Never rely on a silent clipboard write as the sole delivery of a load-bearing value.

### 26. [HIGH] Confirming a refund is a single unguarded click. The green CheckCircle icon-button in the Actions column calls handleConfirmRefund(reg.id) immediately, with no confirmation dialog and no undo. The same visual (a green check) is also used elsewhere as a generic success/approve glyph.
- **Group / page:** Registrations, Members & Kiosk — CampaignRegistrations.js (Confirm Refund action, lines ~778-788)
- **Principle:** Nielsen #5 Error Prevention / #6 Recognition over Recall
- **Why it matters:** This posts a real, money-moving refund confirmation. In a dense table with icon-only actions, a mis-tap on the wrong row confirms a refund that cannot be taken back, and the ambiguous icon gives no hint of the severity before clicking.
- **Recommendation:** Require a confirmation step naming the registrant and refund amount ('Confirm refund of ₹X to Jane Doe?'). Give the action a distinct, labeled control (e.g. a 'Confirm refund' text button in the row-expand or detail view) rather than a bare green check shared with unrelated success states.

### 27. [HIGH] In Kiosk payment, 'Amount Received' is a freely editable number input pre-filled with amount_due, and confirmPayment only checks amount > 0. A volunteer can confirm any amount — well under or over the amount due — and it commits with a success screen and no warning.
- **Group / page:** Registrations, Members & Kiosk — KioskMode.js (confirmPayment, amountReceived input)
